# Contributing to Arena.ai Android Client

Thank you for your interest in contributing to the unofficial Arena.ai Android client!

## Code of Conduct

Please read and follow our [Code of Conduct](CODE_OF_CONDUCT.md) in all community interactions.

## How to Contribute

1. **Fork the repository** on GitHub.
2. **Clone your fork** locally:
   ```bash
   git clone https://github.com/<your-username>/arena-ai-android.git
   cd arena-ai-android
   ```
3. **Create a topic branch**:
   ```bash
   git checkout -b feature/my-new-feature
   ```
4. **Make your changes**:
   - Ensure changes in `android/` follow Android best practices.
   - Run unit tests and verify the Gradle build compiles cleanly.
   - Run the automated compliance test suite (`npm test`) from the root directory.
5. **Commit your changes**:
   - Use clear, conventional commit messages (e.g., `feat: ...`, `fix: ...`, `docs: ...`).
6. **Push to your branch and submit a Pull Request**:
   - Provide a clear description of the problem solved and the testing performed.

## Building & Testing from Source

### Prerequisites
- JDK 17 or higher
- Android SDK (API 34/35 platform and build-tools)
- Node.js 20 (pinned in `.nvmrc`) for the compliance test suite
- Gradle 8.14 (use the included wrapper, which is committed executable)

### Running Tests

From the repository root:
```bash
# Install the test harness once
npm ci

# Run the compliance, capability, artifact and release-engineering suite
npm test

# Or: installs dependencies, runs the suite, then Gradle when a JDK is present
./test.sh
```

From the `android/` directory:
```bash
# Run Android Java unit tests
./gradlew test
```

### Compiling APKs
Navigate to the `android/` directory:
```bash
cd android

# Build debug APK
./gradlew assembleDebug

# Build signed release APK
./gradlew assembleRelease
```

APK outputs are placed in `android/app/build/outputs/apk/`.

### Release Signing

Release builds read the keystore from Gradle properties or environment variables:

| Variable | Purpose |
| :--- | :--- |
| `ARENA_RELEASE_STORE_FILE` | Absolute path to the `.jks`/`.keystore` |
| `ARENA_RELEASE_STORE_PASSWORD` | Keystore password |
| `ARENA_RELEASE_KEY_ALIAS` | Key alias |
| `ARENA_RELEASE_KEY_PASSWORD` | Key password |

Never commit the keystore or its passwords, and never use a keystore generated by CI.

### Cutting a release

Read [`RELEASE.md`](RELEASE.md). In short: bump the versions, update
`release_notes.md`, run `./scripts/release-check.sh`, then push a matching tag. The
`release` workflow builds, verifies the signature against the documented certificate and
publishes the APK plus `SHA256SUMS`.

### Local development proxy

`server.js` is an optional inspection proxy; the app never needs it.

```bash
./start.sh                     # npm ci + npm start
docker compose up --build      # or run it in a container
```
Without these variables `assembleRelease` prints a warning and falls back to the debug
key; such an APK cannot be installed over a properly signed release and must not be
published. `.github/workflows/release.yml` refuses to publish in that case.

### Verifying an APK

```bash
scripts/verify-apk.sh android/app/build/outputs/apk/release/app-release.apk
```

The script checks APK Signature Schemes v1/v2/v3, the signing certificate, 4-byte zip
alignment, package metadata and the SHA-256 checksum.

### Native Capability Bridge

The app intentionally adds no UI of its own. When changing `MainActivity`,
`DownloadHandler`, `AppUpdateManager` or `UpdateVerifier`, keep the following contract:

- every new screen must come from the Arena web app, not from native layout code;
- transient system surfaces (dialogs, share sheet, notification shade, package
  installer) are acceptable where the web platform has no equivalent;
- the navigation allow-list, permission set and download/update verification paths
  must not be weakened. The audit suite (`npm test`) enforces this.
