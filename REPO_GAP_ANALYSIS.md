# Arena AI Android — Repository Gap Analysis

**Repository:** `Mr-Nobody-Anonymous/arena-ai-android`  
**Branch audited:** `arena/89f2305c-arena-ai-android` at `f3f2626` (v1.0.3)  
**Date:** 2026-10-18  
**Method:** full source review, `npm ci` + `npm test`, APK/ZIP/certificate inspection (`unzip`, `openssl`, `pyaxmlparser`), GitHub release/CI inspection.

---

> **Update (same day):** every finding below has been triaged in the **Implementation status** section immediately after this summary. Several items were deliberately closed as "not done" because they would add native UI.

## Bottom line

The project **builds and its 36-check test suite passes**, and the APK's checksum, package name, version, and zip alignment are correct. However, the **release and update trust chain is broken**:

- CI generates a **new signing key on every run**. There is no stable release key.
- The committed APK is signed with a **different certificate than the one documented** in the README, audit report, and release notes.
- The APK has **v1 + v2 signatures only**, not v3 as claimed.
- The in-app updater downloads an APK but **does not verify its hash or signature** before installing it.
- The README's main download button still points to **v1.0.2**, not v1.0.3.
- Documentation claims the app requests only `INTERNET`; the APK actually also requests `REQUEST_INSTALL_PACKAGES`.

In practice, the advertised "install future updates inside the app" workflow can fail with Android's *"App not installed"* / `INSTALL_FAILED_UPDATE_INCOMPATIBLE` error because the next build is signed with a different key.

## 1. Critical / release-blocking

### C1. The signing key changes on every CI run — updates cannot be installed

**Where:** `.github/workflows/build.yml:30-33`, `android/app/build.gradle:19-31`, `.gitignore`

The workflow runs `keytool -genkey` on every build:

```yaml
- name: Generate Community Release Keystore
  working-directory: android/app
  run: |
    keytool -genkey -v -keystore release.keystore -alias arenaai ...
```

`release.keystore` is git-ignored, no signing secret is configured, and the key is never uploaded or reused. Every CI run therefore produces a **different certificate**.

**Impact:**

- Android only allows an update if the new APK has the same signing identity as the installed app.
- A user who installed the v1.0.2 artifact cannot install the v1.0.3 artifact produced by a different CI run. The in-app updater will download the new APK and the package installer will reject it.
- This directly contradicts `README.md:207-215` ("All subsequent updates can now be installed directly inside the app") and the v1.0.3 release note calling itself a "live upgrade target verifying the automated in-app updater."
- The README troubleshooting table already lists "App not installed as package appears to be invalid" → "Uninstall the old version first." That is a workaround for the symptom, not a fix.

**Evidence that a key rotation already happened:**

| Property | Documented | Actual committed APK |
|---|---|---|
| SHA-256 cert fingerprint | `7B:7C:33:2A:78:9C:48:F2:97:95:46:08:11:F6:B7:31:B6:F2:B0:62:29:9C:AD:71:A5:CB:E4:59:EC:E8:2F:49` | `0A:78:95:E6:52:C7:F1:9C:58:8A:DD:1A:B8:40:B4:C5:EE:32:EA:C1:64:55:89:27:0F:34:65:05:99:D3:F2:DE` |
| SHA-1 cert fingerprint | `A1:B9:F5:28:82:4A:63:0F:AA:2B:77:B5:F7:AF:2A:BB:BF:D7:01:1D` | `DA:EA:97:45:CC:72:1D:E6:F4:D1:8A:A8:DA:43:53:0A:E3:86:BA:A4` |
| Signature algorithm | `SHA384withRSA` | `sha256WithRSAEncryption` |
| Certificate validity | Oct 11, 2026 → Feb 26, 2054 | Oct 12, 2026 13:06:22 GMT → Feb 27, 2054 13:06:22 GMT |

The certificate subject/issuer and 2048-bit RSA key size match, but the key material does not. This is exactly what a regenerated key looks like.

**Fix:** create one long-lived release keystore, store it and its passwords in GitHub Actions secrets, sign only in a protected release environment, publish the certificate fingerprint, and document a key-rotation/backup policy. Never generate a release key inside CI.

### C3. The self-updater does not verify the APK it installs

**Where:** `android/app/src/main/java/ai/arena/mobile/AppUpdateManager.java`

The updater:

1. Calls `https://api.github.com/.../releases/latest`.
2. Picks the first asset whose name ends in `.apk`.
3. Downloads it over HTTPS.
4. Immediately launches the package installer.

It does **not**:

- compare a SHA-256 hash against the release's `SHA256SUMS` or GitHub's asset digest;
- verify the APK signer certificate/fingerprint;
- check the package name (`ai.arena.mobile`) or version code;
- validate `Content-Length` vs bytes downloaded;
- reject an HTML error page saved as `.apk`.

A `grep` for `MessageDigest`, `SHA-256`, `sha256`, `digest`, `Signature`, or `getPackageArchiveInfo` in `android/app/src/main/java` returns **nothing**.

**Impact:** HTTPS and Android's signature check are the only protections. If the release asset is replaced with a different APK signed by the same key (or if users install a build signed with a different key), there is no application-level integrity check. README/SECURITY claim "verified" updates without this check.

**Fix:** verify the release asset's SHA-256 against a signed checksum, verify the signer certificate fingerprint, verify package name/version, and install through `PackageInstaller` with a session. Reject mismatches before prompting the installer.

### C4. Release builds can silently fall back to debug signing, with a hard-coded password

**Where:** `android/app/build.gradle:19-31`, `:40-42`

```gradle
signingConfigs {
    release {
        if (file("release.keystore").exists()) {
            storeFile file("release.keystore")
            storePassword "arena1234"
            keyAlias "arenaai"
            keyPassword "arena1234"
        } else {
            initWith(signingConfigs.debug)   // silently signs "release" with debug key
        }
        v1SigningEnabled true
        v2SigningEnabled true
    }
}
...
debug {
    signingConfig signingConfigs.release      // debug APK gets release key when present
}
```

- Passwords are committed in plain text.
- If a contributor runs `./gradlew assembleRelease` without `release.keystore`, the output is a **debug-signed release APK**. It will not install over any official build.
- CI works only because it happens to generate a keystore first; local release builds are not reproducible.
- Debug builds use the release signing config, which is the reverse of normal hygiene.

**Fix:** read keystore path/passwords from environment or Gradle properties, fail the build if missing, and keep debug and release signing configs separate.

### C5. APK has v1 + v2 signatures, but no v3 — docs claim v1 + v2 + v3

**Where:** `android/app/build.gradle:29-30`; APK signing block

The configuration enables v1 and v2 only. Inspecting the APK's APK Signing Block yields:

- `APK Sig Block 42`: present
- v2 block ID `0x7109871a`: present
- v3 block ID `0xf05368c0`: **absent**
- v3.1 block ID `0x1b93ad61`: **absent**

This false claim appears in:

- `README.md:68`, `:175`, `:242`
- `ANALYSIS_REPORT.md:31`, `:64`
- `SECURITY.md:31`
- `CHANGELOG.md:71`
- `release_notes.md:54`

v2 is enough for installation on Android 11–15, so this is not an install blocker — but the security documentation is false. Add v3 signing explicitly if that is the claim, then verify with `apksigner verify --print-certs`.

## 2. High-priority findings

### H1. Documented certificate values are wrong

See the table under C1. The subject/issuer text and key size are right; the fingerprint, algorithm, and validity dates are wrong.

**Impact:** anyone who verifies the APK against the README will conclude it is tampered with. The "Verified Release" badge is not backed by matching values.

**Fix:** regenerate the signing section from the real certificate, add the exact `apksigner verify --print-certs` command, and update all five documents at once.

### H2. Privacy/Security say only `INTERNET`; the manifest also declares `REQUEST_INSTALL_PACKAGES`

**Where:** `android/app/src/main/AndroidManifest.xml:5-7`, `PRIVACY.md:44-45`, `SECURITY.md:26`

Actual APK permissions parsed from `AndroidManifest.xml`:

- `android.permission.INTERNET`
- `android.permission.REQUEST_INSTALL_PACKAGES`
- `ai.arena.mobile.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` (generated by AndroidX)

`PRIVACY.md` says "The application requests only a single Android permission" and `SECURITY.md` says "requests solely `android.permission.INTERNET`". Both are false. `REQUEST_INSTALL_PACKAGES` is a sensitive install-unknown-apps capability and should be disclosed with its purpose and behavior.

The audit test at `tests/test-suite.js:104` is named "Minimal Permissions (INTERNET only...)" but only checks that `INTERNET` exists and `ACCESS_NETWORK_STATE` does not. It happily passes despite the extra install permission.

**Fix:** update both documents and make the test assert the exact permission set.

### H3. The APK contains no LICENSE or NOTICE, and the app has no About/licenses screen

**Evidence:** `unzip -l ArenaAI.apk | grep -iE "license|notice|privacy"` returns nothing.

The repository has `LICENSE` (Apache-2.0) and `NOTICE`, but the distributed binary does not. Apache-2.0 requires recipients of a binary to receive a copy of the license and applicable notices. There is also no in-app About, privacy policy, open-source licenses, or "unofficial" disclaimer screen — the app is a pure WebView shell.

`NOTICE` is also incomplete/inaccurate:

- It omits Kotlin stdlib and kotlinx-coroutines, both present in the APK (`kotlin/`, `DebugProbesKt.bin`).
- It lists "Material Components for Android" although the app does not declare the Material dependency.
- It lists JUnit/AndroidX Test, which are test-only and not in the release APK.

**Fix:** bundle `LICENSE`/`NOTICE` in the APK (or add an in-app licenses screen via `androidx.core`/a WebView asset), correct the NOTICE inventory, and add an in-app About/privacy link.

### H4. There is no release workflow, signing secret, or APK verification in CI

**Where:** `.github/workflows/build.yml`

The only workflow builds and uploads an artifact. It does **not**:

- trigger on tags or `workflow_dispatch`;
- call `apksigner verify`, `zipalign -c`, or `aapt dump badging`;
- compare the built APK's SHA-256 to the committed `SHA256SUMS`/documented hash;
- attach the APK and checksums to a GitHub Release;
- use a stable signing secret or protected `release` environment;
- validate the Gradle wrapper (`gradle/actions/wrapper-validation`);
- run `./gradlew lint`;
- run `npm audit`;
- run instrumentation tests;
- use least-privilege `permissions`, `concurrency`, or `timeout-minutes`;
- cache Gradle/npm.

It also uses `npm ci || npm install` (`build.yml:45`), which hides lockfile problems instead of failing.

**Fix:** add a tag-triggered `release.yml` with a protected environment, stable keystore secret, version bump check, `apksigner verify`, `zipalign -c -v 4`, checksum generation/comparison, artifact attestation, and `gh release upload`. Keep the build workflow for PRs with `permissions: contents: read`.

### H5. Update checks run on every page load and repeat the dialog

**Where:** `MainActivity.java:298-305`, `AppUpdateManager.java`

- `onPageFinished` calls `AppUpdateManager.checkForUpdates(...)` for every successful HTTPS page. A user navigating through login, OAuth, leaderboard, and chat pages may hit the GitHub API dozens of times.
- The GitHub API is unauthenticated (60 requests/hour/IP); normal browsing can exhaust it.
- There is no "checking" guard, so multiple page finishes can stack multiple `Update Available` dialogs.
- Tapping **Later** does not record anything; the same dialog returns on the next page load.
- There is no "skip this version" preference.
- `releaseJson.optString("body", "")` is read at `AppUpdateManager.java:75` but never displayed.

**Fix:** check once per app session and at most once every 24h; persist `lastChecked` and `skippedVersion`; show release notes; guard with an `isChecking` flag.

### H6. No robust WebView failure handling

Missing handlers (verified by source grep):

- **`onRenderProcessGone`** — if the WebView renderer crashes, the host app is killed with it. A simple recovery (destroy/recreate WebView) is absent.
- **`onReceivedHttpError`** — HTTP 5xx/maintenance pages do not trigger the reconnect screen or retry logic.
- **WebView package availability check** — if Android System WebView is disabled/missing/outdated, `new WebView(this)` can throw and crash the app with no fallback.

**Fix:** add `onRenderProcessGone` recovery, show the offline screen for main-frame 5xx, wrap WebView creation in a try/catch with a clear message, and handle SSL errors explicitly.

### H7. "Download Management" is not a download manager

**Where:** `MainActivity.java:419-431`; claim at `README.md:197`

The entire download handler is:

```java
@Override
public void onDownloadStart(String url, String userAgent, String contentDisposition,
                            String mimeType, long contentLength) {
    Intent downloadIntent = new Intent(Intent.ACTION_VIEW);
    downloadIntent.setData(Uri.parse(url));
    startActivity(downloadIntent);
}
```

It ignores the user agent, cookies, `contentDisposition`, MIME type, and length. Downloads that require the Arena session will fail because the browser app does not share the WebView cookies. `blob:` and `data:` downloads cannot be handled this way. There is no notification, filename, progress, or destination control.

**Fix:** use `DownloadManager.Request` with the WebView cookie header and a destination, or remove the README claim. Handle `blob:`/`data:` separately.

### H8. OAuth popup WebViews leak and are under-validated

**Where:** `MainActivity.java:366-414`

# Zip alignment / stored entries

import zipfile, struct
d = open('ArenaAI.apk','rb').read()
z = zipfile.ZipFile('ArenaAI.apk')
bad = 0
for i in z.infolist():
    n, e = struct.unpack('<HH', d[i.header_offset+26:i.header_offset+30])
    off = i.header_offset + 30 + n + e
    if i.compress_type == 0 and off % 4:
        bad += 1
print('stored:', sum(1 for i in z.infolist() if i.compress_type == 0), 'misaligned:', bad)
PY
